# 取关狗 v0.2.73：连续扫描限流优化（2026-11-03）

## 问题与根因
v0.2.72 的关注/粉丝读取有两套路径。快速 GraphQL 游标分页每页等待约 2.5–4.5 秒，DOM 模式每轮滚动等待约 0.76–1.48 秒；在数千账号连续扫描时请求密度偏高。X 的 HTTP 429 是服务端限制，重开窗口、新建插件或重置进度均不能使账号额度恢复。此前扫描已经读取的 3,797 关注、2,438 粉丝也可能占用尚未重置的请求配额。

## 本次更新
- 快速游标分页常规等待 7–10.5 秒；每 5 页改为 14–22 秒，每 18 页休息 35–50 秒。最近两小时遇到过 429 的检测进一步降低请求频率。
- DOM 读取也调整每轮滚动间隔；每新增约 85–130 位账号休息 10–18 秒。
- 遇到真正的 429 后停止请求，保留游标和已采集账号，尊重服务端可用的 Retry-After / x-rate-limit-reset，等待时间取服务端指示与本地退避中的较长者。
- 连续 429 计数不再因偶尔成功读取少数账号而立刻清零；重建窗口也不清除最近的限流失败历史。
- 冷却期间不能通过新建扫描立即重试；已有暂停扫描的断点时不能误用“新建扫描”覆盖旧数据，需继续原任务或明确清理。

## 验收与局限
- `npm run test:scan` 五项针对限流、时间窗口、HTTP 429 响应头、计数保护的新测试通过。
- 隔离 Chrome 测试：手动强制重开真实 popup、模拟冷却到期后恢复、模拟保存 3,797／2,438 账号的断点迁移、禁止新建覆盖暂停断点均通过；模拟 X 页面和隔离浏览器，不访问用户真实 X 账号。
- 十语言本地化与多浏览器 Manifest 沿用 v0.2.72；三个 v0.2.73 ZIP 结构和内容校验完成。
- 原仓库 14 个旧 Node 测试中有 10 个因旧版本测试夹具不支持 chrome.alarms 等新 API 而失败；这些失败在原 v0.2.72 Git 提交中已经存在（4 通过/10 失败），不是本次 v0.2.73 引入。v0.2.73 是 8 通过/10 个旧测试失败，其中 5 个新专项测试通过。不能声称全量旧测试通过。
- 未在真实账号经历完整 6,295 人连续扫描及真实 HTTP 429 的跨小时恢复，也未在 Edge/Firefox 原生浏览器全量验证；不保证以后完全避免 429。
- 较保守的节奏会增加一次大规模扫描所需时间，但避免短时间内请求大量分页。若 X 账号在此前扫描中已触发限制，请等实际限制结束，不要通过反复重开继续请求。
- 浏览器扩展 storage.local 与扩展 ID 绑定。直接加载不同目录的解压版可能获得不同扩展 ID，因此不会自动继承原断点；请通过同一商店插件 ID 升级，或在确认原安装目录及备份存储数据后原位更新，不要卸载原插件。
