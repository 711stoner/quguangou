## 当前产品说明

取关狗不是个人取关检测器。它不会扫描用户的关注/粉丝历史，也不会告诉用户“刚刚谁取关了你”。项目整理整个 X 中文社区的互关后取关线索，并在用户确认后帮助用户依次拉黑名单账号。

核心定位：

> 不是查谁取关了你，而是整理社区取关记录，帮你一键处理名单中的账号。

扩展说明：

- 用户登录自己的 X 账号。
- 用户先查看在线社区名单；网络异常时自动使用上次缓存或扩展内置备用名单。
- 用户主动点击后，扩展依次打开名单账号主页并尝试拉黑。
- 不读取 X 密码。
- 不上传用户账号数据。
- 不依赖远程服务器完成拉黑。
- 非 X Corp. 官方产品，与 X Corp. 无隶属或认可关系。

## 执行节奏与风险提示

- 每批最多尝试处理 20 个账号。
- 每个账号之间保留约 15 秒操作间隔。
- 一批结束后强制进入 30 分钟冷却期。
- 冷却结束后，下一批仍需用户手动再次点击继续；例如 100 个账号需要分 5 批、手动操作 5 次。
- 冷却期间提供次级“跳过冷却”入口，但必须二次确认风险；默认推荐等待完整 30 分钟。跳过动作记录在本地任务状态中。
- 名单会持续更新，界面提醒用户可以之后回来查看新增名单并继续处理。
- 设计目标是降低短时间连续批量操作频率并保留人工确认节点，但不能保证账号安全。
- X 官方规则禁止非 API 自动化操作；使用可能导致账号受限、暂停或永久停用。
- 页面文案要提醒用户自行阅读平台规则、自行判断风险。

## 名单原则

名单线索主要来自三类来源：

1. X 中文社区公开帖子中对“互关后取关”的曝光记录。
2. 互关帖下主动留言、但主页关注与粉丝比例明显异常的账号线索，例如关注约 1000、粉丝约 3000。比例仅作为待核对线索，不单凭比例认定或收录。
3. 用户私信或公开投稿的“互关后又取关我”记录，并附截图、时间线等材料。

- 线索经人工整理和复核后再进入名单。
- 名单来自整个 X 中文社区，不局限于当前用户自己的关注列表。
- 被收录账号可以说明理由并提交补充材料，申请复核、更正或移除。
- 已经显示“已屏蔽”的账号也可以加入名单。

## 安装说明重点

官网应写清楚：

1. 下载 ZIP。
2. 双击解压。
3. 打开 Chrome 浏览器新标签页。
4. 复制 `chrome://extensions`，粘贴到浏览器最上方的地址栏，不要粘贴到搜索框。
5. 打开“开发者模式”。
6. 点击“加载已解压的扩展程序”。
7. 选择解压后的整个 `quguangou-chrome-v版本号` 文件夹，不要点里面的单个文件。

当前官网还需提示：

- Chrome 0.2.17 已提交商店审核；审核通过前，以商店当前线上版本或官网手动安装包为准。

- 插件打开时优先读取 GitHub Pages 在线名单；失败时依次回退到上次成功缓存和插件内置备用名单。
- 只有插件代码、权限、界面或运行逻辑变化时，才需要重新提交浏览器商店。

## 名单资产保护与未来私有化方案（暂不执行）

当前先保持现状，后续有时间再迁移。不要现在直接把仓库改成 Private。

当前结构：

- GitHub 仓库仍为 Public。
- GitHub Pages 同时承载官网和在线名单。
- 插件当前在线名单地址为 `https://711stoner.github.io/quguangou/extension/data/blocklist.json`。
- 插件从 v0.2.14 起已经支持“在线名单 → 本地缓存 → 插件内置备用名单”的回退机制。
- 因此现在只更新 `extension/data/blocklist.json` 并推送 GitHub，就可以让 Chrome / Edge / Firefox 已安装版本读取新名单，不需要重新提交商店。
- 2026-09-24 已从官网页脚删除公开 GitHub 入口，但这只隐藏了入口，不等于名单已经私有。
- 当前完整名单文件及部分名单核对截图仍存在于公开仓库中，因此核心名单资产实际上仍可被直接读取。

未来目标：

> 私有源码 / 私有名单 / 私有证据库 → 一键发布名单 → 独立远程数据服务 → Chrome / Edge / Firefox 自动读取最新版

建议未来迁移到独立的数据接口，例如 Cloudflare Worker 或其他可控 API，不再让插件直接依赖公开 GitHub Pages 的 `blocklist.json`。

理想维护流程：

1. 在本地或私人仓库修改名单。
2. 双击一个“发布名单.command”或执行单一发布命令。
3. 脚本自动校验 JSON 格式、重复账号、版本号和更新时间。
4. 自动把最新名单发布到独立数据服务。
5. 三个浏览器版本继续自动读取最新名单。
6. 单纯增加、删除、纠正名单时，仍然不需要重新上传 Chrome / Edge / Firefox 商店。
7. 只有插件代码、权限、界面或运行逻辑变化时，才重新发布扩展。

仓库私有化顺序：

1. 先建立新的远程名单服务。
2. 修改插件，让在线名单地址改为新的 API / Worker。
3. 发布一次新的 Chrome / Edge / Firefox 版本。
4. 确认三个商店的新版本都能稳定读取新名单，并保留缓存 / 内置备用名单回退。
5. 再把 GitHub 仓库改为 Private。
6. 最后检查官网、隐私政策、支持页和文档中是否还有公开 GitHub 链接或旧名单地址。

重要限制：

- 如果新的远程接口仍然一次性把完整名单 JSON 返回给插件，那么技术上用户仍可以从网络请求或扩展缓存中取得整份名单。
- 如果以后名单确实被视为核心数据资产，更强的保护方式是由服务器按账号查询、分页或分批返回，而不是公开一个可一次下载完整名单的固定 JSON。
- 在新数据源完成并且新版插件上线前，不要直接把当前 GitHub 仓库设为 Private，否则现有 GitHub Pages 官网和在线名单链路可能中断。
- 未来迁移的目标不是改变“取关狗”现有产品定位，而只是把公开产品、插件代码与核心名单资产分离。

### “包裹上的标题”和“软件包摘要”为什么不能修改

Chrome Web Store 后台中的：

- “包裹上的标题”来自 `manifest.json` 的 `name`。
- “软件包摘要”来自 `manifest.json` 的 `description`。

这两个字段由扩展包决定，上传 ZIP 后在商店后台会被锁定，不能直接编辑。

如果需要修改标题或摘要：

1. 修改 `extension/manifest.json` 中的 `name` 或 `description`。
2. 提高扩展版本号，例如 `0.2.14 → 0.2.15`。
3. 同步更新 `package.json` 和浏览器对应 manifest。
4. 运行测试并重新构建。
5. 生成新的 `quguangou-chrome-v0.2.15.zip`。
6. 在 Chrome Web Store 后台上传新版软件包并重新提交审核。
7. 新版本审核并发布后，Chrome Web Store 上的标题/摘要会随新包更新。

可以先用当前版本上线，之后再通过更高版本修改标题、摘要、功能或权限，不必为了文案问题重新创建商品。
